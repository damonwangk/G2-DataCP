# MCAP回放、姿态与控制诊断使用说明

MCAP动作任务由`robot_replay.py`管理，`sdk_worker.py`调用原`replay/lerobot_replay.py`执行器；`postures.py`保存/检查姿态，`pose_worker.py`实际恢复。`sdk-run.sh`提供worker的厂商SDK环境，`control_session.py`在显式动作开始后交接控制权。网页/API入口为`app.py`、`static/app.js`等。worker需要由后台创建的任务目录和控制文件，日常不逐个直接启动。

## MCAP原始指令回放

先启动平台，在 MCAP 回放区点击“选择文件”选择机器人上的已完成 MCAP，或输入完整路径。回放文件不再绑定采集目录或记录分类。在网页可先读取/核对，再显式点击执行；CLI：

```bash
cd /data/r2_datacp
./datacp mcap-files
# 下面开始实际机器人动作：
./datacp mcap-replay --file episode_1_采集时间 --speed 1
./datacp mcap-replay-status
./datacp mcap-replay-stop
```

`robot_replay.Trajectory`使用`replay/source_episode.py`读取`/hal/joint_cmd`及`/wbc/*_ee_command`原控制指令、名称和Header PTP；不把实测反馈生成动作，不做夹爪指令取反，不自动返回首帧。每个原始事件按顺序读取，事件之间100Hz保持；NULL轴当次不发送，其他轴继续。普通`joint_servo_control(req,False)`、空速度数组沿用原程序。

部分关节回放由API的`controlled_names`指定SDK名称；例如：

```bash
api=http://127.0.0.1:18769
curl -sS -H 'Content-Type: application/json' "$api/api/replay/plan" \
  -d '{"file":"episode_1_采集时间","speed":1,"controlled_names":["idx21_arm_l_joint1","idx31_gripper_l_inner_joint1"]}'
```

`/plan`只读计划；`POST /api/replay/start`使用同样的参数并额外要求`"confirm_motion":true`，会交接控制权并发动作。`start_s`、`duration_s`选择原轨迹窗口，`speed`必须大于0。运行中`POST /api/replay/pause`切换暂停/继续，`POST /api/replay/stop`停止继续发送。

MCAP回放的worker状态在`studio/runtime/replay_<任务编号>/`；包括`control.json`、`progress.json`、`result.json`、`worker.log`、`trace.jsonl`。后台同时在采集目录保存执行反馈MCAP和目标/反馈执行trace。`completed`表示时间轴完成，SDK接受数与实际机械跟随需分别看，不代表实机完全复现。

此网页MCAP路径仍使用原执行器；独立“限幅平滑副本”的入口与规则见[独立回放说明](../replay/README_clamped_smooth.md)，不会因本模块文档整理自动切换。

## 保存、检查、恢复与删除姿态

在网页“初始姿态”区填写名称并保存当前姿态，也可用API：

```bash
api=http://127.0.0.1:18769
curl -sS "$api/api/poses"
curl -sS -H 'Content-Type: application/json' "$api/api/poses" -d '{"label":"采集准备位"}'
# 替换为列表或保存响应中的id：
pose_id=姿态ID
curl -sS -X POST "$api/api/poses/$pose_id/plan"
# 下面开始实际恢复动作：
curl -sS -H 'Content-Type: application/json' "$api/api/poses/$pose_id/restore" -d '{"confirm_motion":true}'
```

保存内容是22个本体关节`motor_position`和左右夹爪各自`end_state[].position`，文件为`studio/poses/<id>.mcap`；不含底盘。保存需要完整且新鲜的反馈；检查只计算与当前位置差值，不发送动作。

恢复先通过`joint_control_request`恢复本体，再用`move_ee_pos`恢复双夹爪；Dahuan在该恢复接口边界按`0.025 - 保存的实测值`换成控制坐标。姿态文件中的实测值不改写，原始指令回放不经过此姿态换算。恢复状态在`/api/state`的`robot_replay`中查看，停止使用`./datacp mcap-replay-stop`或网页停止执行按钮。

删除姿态会移入可恢复目录：

```bash
curl -sS -X POST "$api/api/poses/$pose_id/delete"
```

响应`archived_path`指向`studio/poses/.deleted/`中的原MCAP；撤销时将该文件移回`studio/poses/<id>.mcap`，避免覆盖同名文件。动作期间不能删除正在使用的姿态。MCAP回放、LeRobot/原生回放、姿态恢复与新采集有任务互斥检查，先结束当前任务再切换。

## 范围提醒与控制检测

`sdk_limits.py`根据`config/joint_limits_source.json`产生24位置的范围提示；`control_diagnostics.py`读取注册表、订阅状态及厂商日志。使用网页“检测能否控制（只读）”，或`curl -sS http://127.0.0.1:18769/api/control/check`。这些检查不发送动作、不切换控制权、不更改限位，也不证明当前实机一定跟随。
